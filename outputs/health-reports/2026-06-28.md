### 2. Subagent Pattern 3 "Agent Pool" — specialist collaboration vs. homogeneous pool (NEW)

- **Concept page:** `concepts/subagent-patterns.md`, Pattern 3 "Agent Pool":
  > "When to use: Multi-step workflows where **specialists need to collaborate** (researcher + writer; coder + reviewer). The main agent routes information between them."
- **Source page:** `sources/philschmid/subagent-patterns-2026.md`, Pattern 3:
  > "Agent Pool — orchestrator delegates to a pool of **identical agents**; used for **homogeneous parallelism**. **Don't use a pool if agents need different specializations** — use Teams instead."

The concept page describes Pattern 3 as a specialist-collaboration pattern (researcher + writer + coder + reviewer), which is what the source's Pattern 4 (Teams) is for. The source's Pattern 3 is specifically for homogeneous, identical-capability agents doing the same type of work in parallel. The concept page conflates these two distinct patterns under a single label.

**Suggested fix:** Review `concepts/subagent-patterns.md` Pattern 3 body. The "When to use" clause should describe homogeneous parallel work (same specialization, many instances), not cross-functional collaboration. Specialist collaboration belongs in Pattern 4 (Teams). A human reviewer should validate the full Pattern 3 / Pattern 4 distinction before editing, as the error may propagate into other sections.

## ❓ Open Questions

1. **When does harness investment become net-negative?** The wiki argues "build to delete" and "thin harness" (Bitter Lesson) while also describing increasingly sophisticated infrastructure (brain/hands decoupling, event log durability, credential isolation, vault memory). No guidance exists on which harness layers are durable investments vs. transient ones that the model will absorb. A framework distinguishing "security and observability" (likely durable) from "retrieval and routing" (likely transient) would be the most actionable addition for engineering leads deciding where to invest.

2. **How should memory quality itself be evaluated?** `evals-and-graders.md` covers task output evaluation thoroughly. The Dreaming architecture produces a memory store diff as the accountability mechanism, but no eval framework for memory quality exists in the wiki — e.g., coverage (important patterns captured?), precision (no false memories?), freshness (stale entries pruned?). The 97%/6× production results are outcome metrics, not diagnostic ones. An engineering team wanting to improve memory quality has no measurement starting point.

3. **What is the right granularity for subagent boundaries?** The wiki describes *when* to use subagents (parallelism or fresh perspective) but not *how fine-grained* those boundaries should be. Should every distinct reasoning task be a potential subagent boundary? The communication breakdown failure mode (well-documented in `subagent-patterns.md`) implies that more boundaries introduce more coordination risk. No guidance exists on optimizing this tradeoff — coarser boundaries (fewer subagents, more context per agent) vs. finer ones (more isolation, more handoff overhead).

4. **Can autoresearch close the eval saturation loop without humans?** The wiki flags that static benchmarks get saturated at autoresearch speeds and suggests pulling from production data. But no source describes a mechanism for autonomously evolving an eval suite. If a human must continuously update evals to prevent saturation, autoresearch remains human-bound at a different layer — the automation benefit is bounded by human eval-update bandwidth.

5. **When will skill architecture itself become technical debt?** The wiki notes that capability skills become obsolete as models improve (retire when evals pass without the skill). But the architecture itself — index → load → runtime tiers, SKILL.md format, trigger-description routing — is not immune to the Bitter Lesson. As models become better at reading context, will the skill dispatch mechanism itself dissolve into model behavior? The wiki treats skill architecture as a stable investment but never addresses its own obsolescence trajectory.
