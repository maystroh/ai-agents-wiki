## 🔴 Contradictions

### 1. "Inner vs Outer Harness" — concept page and source page define the term differently (NEW)

- **Page A:** `concepts/agent-harness.md`, "Inner vs Outer Harness" section (attributed to "Böckeler's harness engineering article"):
  > "**Inner harness**: what the model builder ships — Anthropic's Claude Agent SDK, Cursor's Auto, Codex's app server.
  > **Outer harness**: what the *user* assembles on top — AGENTS.md, MCP servers, custom skills, org-specific code review agents."
- **Page B:** `sources/philschmid/agent-harness-2026.md`, Key Insights:
  > "**Inner harness (within turn) vs Outer harness (across sessions).** Inner: compaction, tool routing, error recovery. Outer: memory, learning, capability expansion."

These are not two shades of the same idea — they are two different axes. The concept page splits the harness by **who ships it** (vendor vs. user). The source page splits it by **temporal scope** (within-turn vs. across-session). A reader who takes the concept page's definition and then reads the source page's will mis-map every example. Compounding this, the concept page attributes the distinction to "Böckeler," who has no source page and no entry in `entities/people.md` (see Data Gap 9), while the wiki's *own* Philipp Schmid source page presents the same term as one of its key insights.

**Suggested fix (human):** Decide which definition the wiki endorses. If both framings are real and distinct, the section should present them as two separate axes with different names, and the Böckeler attribution needs a source page. This is a section rewrite, so it is flagged rather than auto-fixed.

## 🟢 Missing Concept Pages

### 1. Parallel Agent Workflows / "Multi-Clodding" (NEW)

**Sources that mention it:** `stop-babysitting-agents` ("multi-clodding" — parallelizing without fragmenting attention), `boris-cherny-claude-code` (hundreds-to-thousands of parallel agents per user; Auto Mode as the permission layer that makes it viable), `how-to-work-with-ai` (3–6 parallel sessions via git worktrees; pair-programmer pattern across tmux panes), `beyond-basics-claude-code` (Claude Agents terminal as an orchestration dashboard), `vibe-to-agentic-engineering` (Karpathy: coordinating agents *is* the discipline) — **5 sources**.

**What the page should cover:** Human-directed parallelism, as distinct from agent-directed delegation. `subagent-patterns.md` covers an *agent* orchestrating other agents; nothing covers a *person* running N agents at once — the workspace mechanics (git worktrees, separate checkouts), the attention economics (how many concurrent agents before the human becomes the bottleneck), the review surface (how you inspect N parallel diffs), and the permission/trust layer (Auto Mode) that makes unattended parallelism safe.

**Why it earns its own page:** It has a distinct definition, a genuine non-obvious tradeoff (parallelism gains vs. human attention fragmentation — the explicit subject of the "multi-clodding" framing), and five sources to synthesize. It is currently the largest well-sourced topic in the wiki with no home. Practitioners ask "how many agents can I actually run at once?" and the wiki has no answer.

## ❓ Open Questions

1. **Which "inner/outer harness" split is the useful one — vendor-vs-user, or within-turn-vs-across-session?** Contradiction 1 is a symptom of a real conceptual question. These two axes cut the harness very differently, and they imply different answers to "what should I build?" The vendor/user split says: don't rebuild what your vendor ships. The temporal split says: don't confuse per-turn plumbing with cross-session learning. Both are defensible; the wiki currently asserts both under one name and never reconciles them.

2. **When does harness investment become net-negative?** The wiki preaches "build to delete" and "thin harness" while simultaneously documenting ever-more-sophisticated infrastructure (brain/hands decoupling, event-log durability, credential isolation, DSL interpreters, vault memory). No framework separates harness layers that are durable investments (security, observability, audit) from those the model will absorb (retrieval, routing, planning scaffolds). Engineering leads have no principled way to decide where to spend.

3. **How many agents can one human actually supervise?** The wiki cheerfully cites "hundreds to thousands of parallel agents per user" (Boris Cherny) alongside "multi-clodding without fragmenting attention" (Sid Boudesaria) and "3–6 parallel sessions" (Eugene Yan) — spanning three orders of magnitude. Nobody reconciles them. The binding constraint is human review bandwidth, and the wiki has no model of it. This is the practitioner question the missing Parallel Agent Workflows page would have to answer.

4. **How should memory quality itself be evaluated?** `evals-and-graders.md` covers task-output evaluation thoroughly. Dreaming produces a memory-store diff as its accountability surface, but there is no eval framework for memory *quality* — coverage (were the important patterns captured?), precision (any false memories?), freshness (is stale content pruned?). The 97%/6× figures are outcome metrics, not diagnostics — and per Data Gap 8, they have no baselines either.

5. **Can autoresearch close the eval-saturation loop without humans?** The wiki states plainly that static benchmarks saturate at autoresearch speeds and that eval suites must "evolve" — but no source describes a mechanism for *autonomously* evolving one. If humans must keep hand-updating evals, then autoresearch remains human-bound at exactly the layer it claims to automate, and Jack Clark's 2028 forecast has an unexamined dependency.
